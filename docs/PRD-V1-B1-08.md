## 1. 阶段目标

B1.8 不扩展新的大功能域，而是对 B1.1-B1.7 已交付的身份与权限、首页与导航、政策库、历史问答、分类、政策问答入口、咨询闭环、运行与演示能力进行系统检查和持续迭代。目标是让现有功能从“流程可用”提升到“行为正确、体验完整、状态清晰、边界可靠、可以稳定验收”。

本阶段采用持续问题驱动方式：项目负责人不断提出实际使用中发现的问题；每个问题均需完成复现、期望确认、影响分析、实现、回归验证和 PRD 记录。聊天结论不作为唯一依据，本文件是 B1.8 产品范围、问题状态和验收结论的主记录。

## 2. 范围与原则

| 范围 | 内容 |
|---|---|
| 本阶段包含 | 现有功能缺陷修复；交互、视觉、文案、响应式与可访问性优化；加载、空、错误、无权限和重复操作状态完善；权限、数据边界及跨角色流程修正；性能与开发运行体验优化；必要的自动化回归测试和文档更新 |
| 条件纳入 | 为修复现有流程所必需的小范围 API、数据结构或迁移调整；必须先明确影响、回滚和验收方式，并建立对应 TECH/OpenSpec 变更 |
| 默认不包含 | 新业务模块、未确认的大范围重构、真实 RAG 后端交接、模型或供应商选型、无关数据导入、生产发布、破坏性数据清理 |

执行原则：

- 以用户可观察的问题和明确期望为起点，不为了“顺手优化”扩大范围。
- 修复不得削弱既有鉴权、角色、地区、部门、RLS、隐私及安全失败边界。
- 每个问题独立编号、独立验收；一个问题可以涉及多个文件，但必须有一个明确结果。
- 涉及需求合同、API、数据库、权限或跨模块行为的改动，编码前更新本 PRD，并建立或更新对应 TECH/OpenSpec。
- 小型实现缺陷可以直接修复，但仍须补充与风险相称的测试和本 PRD 证据。
- 不把临时演示数据、Mock 或静默降级当成问题修复。

## 3. 问题闭环流程

每个问题按以下状态推进：

`待确认 -> 已确认 -> 实现中 -> 待验收 -> 已完成`

无法继续时标记为 `阻塞`，并写明所需决策或外部条件；确认不处理时标记为 `不纳入` 并保留原因。

| 步骤 | 必须记录的内容 | 完成条件 |
|---|---|---|
| 1. 发现 | 用户场景、入口、操作、实际表现；可附截图或错误信息 | 能稳定复现，或已有充分证据定位 |
| 2. 确认 | 期望行为、优先级、纳入/不纳入决定 | 产品期望无关键歧义 |
| 3. 分析 | 根因、影响模块、权限/数据/回归风险 | 确定最小合理改动和验证范围 |
| 4. 实现 | 代码、配置、文档或数据变更 | 变更完成且不引入未授权范围 |
| 5. 验证 | 定向测试、相关回归、必要的桌面/移动浏览器核验 | 实际行为符合期望，相关门禁通过 |
| 6. 收口 | 结果、证据、遗留项和必要的 OpenSpec 状态 | 本表更新为已完成或明确阻塞/不纳入 |

## 5. 问题详单

### B18-000 | 建立 B1.8 阶段机制

- **背景：** B1.7 已完成第一批跨模块联调，但后续仍需基于实际使用持续发现并解决现有功能问题。
- **决定：** 在进入 B2.x 新功能前增加 B1.8，集中完成现有能力的检查、修复和优化。
- **结果：** 建立本 PRD 和问题台账；`DEVELOPMENT_STATUS.md` 以 B1.8 为当前步骤。
- **边界：** 本项只建立阶段与记录机制，不代表所有既有功能已重新验收。

### B18-001 | 完善公开首页三类服务入口

- **实际表现：** 未登录首页仍显示全局导航和右侧登录；页面只提供个人、企业两张主卡片，另以小字显示“登录政通惠”；个人和企业卡片先跳到无必要的受保护角色页，再由守卫引导登录。
- **期望行为：** 公开首页不显示全局页头；主内容以“政通惠”为大标题、“一站式政策服务平台”为副标题；个人服务、企业服务、政府服务为三张等尺寸主入口卡片，移除小字登录入口。
- **导航决定：** 三张卡片都直接打开 `/login`。页面在不改变 URL 的前提下保留本次入口意图；登录成功且后端返回对应角色后，个人/企业进入统一登录后首页 `/homepage`，政府进入 `/government`，继续沿用既有服务端角色授权。直接访问登录页时默认进入 `/homepage`。
- **政府账号：** 既有 35 个政府账号从“政府服务”入口登录；本项不创建账号、不修改密码或部门绑定。
- **视觉决定：** 桌面端三卡等宽并列；窄屏改为单列，卡片尺寸与内容层级一致。政府卡片先复用仓库内已有正式服务图片并采用独立裁切，不引入外部热链或未授权素材。
- **范围边界：** `/personal`、`/enterprise`、`/government` 继续作为登录后的真实角色工作区，不删除路由；登录错误、忙碌、配置缺失和权限拒绝行为保持不变。
- **实现结果：** 公开根路径在未登录、身份加载或登录配置缺失状态下不渲染全局页头；主内容显示品牌标题和副标题。三张入口均直接链接 `/login` 并通过路由 state 携带角色意图。个人/企业登录后的默认落点由 B18-006 统一为 `/homepage`，政府仍进入 `/government`；登录决策只依据 `/me` 返回的真实角色。
- **验收证据：** 前端全量测试通过；生产构建通过（93 modules）；OpenSpec strict 通过。浏览器 `1440x900` 实测无页头/导航，三卡均为 `387x217` 且同排、无横向溢出；个人、企业、政府三张卡片分别点击后均直接到 `/login` 并显示登录表单。`390x844` 实测三卡均为 `354x266` 单列、页面宽度 390px、无横向溢出或重叠；控制台无 warning/error。
- **遗留视觉项：** 政府入口当前复用本地企业服务图片并使用不同裁切；不影响本项逻辑验收，后续可在获得合适授权素材或可用图像生成能力后单独替换。

### B18-002 | 登录入口与账号角色不匹配引导

- **实际表现：** 用户从政府服务入口进入登录页后输入个人账号，认证成功后被静默带到个人工作区，用户无法确认是入口选错还是账号错误。
- **期望行为：** 登录成功但账号真实角色与所选入口不匹配时，停留在登录路径并显示阻断式弹窗，不自动进入任何其他角色工作区。
- **弹窗内容：** 明确说明“当前选择的是政府服务，登录账号属于个人服务”等真实角色信息；不显示邮箱、用户 ID、部门绑定或其他敏感资料。
- **操作决定：** 提供“进入个人服务/企业服务/政府服务”（进入账号真实角色对应服务，个人/企业统一进入 `/homepage`）和“切换政府服务/企业服务/个人服务账号”（退出当前会话并回到同一入口登录表单）两个动作。用户必须主动选择，弹窗不支持点击遮罩静默关闭。
- **多角色边界：** 如果账号本身包含所选入口角色，直接进入该入口工作区；若不包含，则以实际可用的个人、企业、政府角色为正确服务。管理员等非三类公开入口角色不伪装成三类服务，返回真实身份首页。
- **权限边界：** 入口意图仍不授予角色；实际角色继续来自后端 `/me`。切换账号必须调用既有退出登录流程清除当前会话，不能只清理前端显示状态。
- **实现结果：** 登录决策已拆分为匹配、不匹配和直接登录三态。政府入口+个人角色返回不匹配状态并停留在 `/login`；阻断式弹窗显示“政府服务/个人服务”，提供“进入个人服务”和“切换政府服务账号”。前者进入统一登录后首页 `/homepage`，后者调用既有 `signOut` 后恢复同一入口登录表单。弹窗使用 `role=dialog`、`aria-modal=true`、标题/描述关联、自动焦点和 Tab 循环，不可通过遮罩关闭。
- **验收证据：** 角色决策测试覆盖政府+政府匹配、政府+个人不匹配、直接登录默认路径；服务端渲染合同确认弹窗不包含邮箱、subject、邮箱/密码表单，包含两个明确动作。响应式合同确认弹窗固定覆盖、内容可滚动、最大宽度 520px，720px 以下按钮单列。前端全量测试通过；生产构建通过（93 modules）；OpenSpec strict 通过；既有 AuthCoordinator 退出测试确认切换账号会调用真实退出网关并先清理会话。
- **真实复测说明：** 自动化验收未使用或输出真实账号凭据，也未主动退出用户浏览器中的会话。可按“政府入口 -> 个人账号”原步骤复测新弹窗及两个分支。

### B18-003 | 登录后角色导航与企业信息

- **实际表现：** 登录后的顶部导航沿用公共项并额外显示“智能分类”“服务状态”和角色工作区入口；个人和企业用户看到的导航不够聚焦，企业没有独立的企业信息入口。
- **期望行为：** 个人用户只显示“首页、政策中心、历史问答、政民互动”四项；企业用户显示上述四项并增加“我的企业”第五项。政府和管理员导航保持现有办理/管理能力，不受本项收缩规则影响。
- **企业信息范围：** “我的企业”只读展示后端 /me 已授权返回的组织名称、组织代码、组织类型、所属地区，以及当前账号显示名/邮箱；缺失字段显示“未设置”，不允许前端编辑或直接写数据库。
- **权限边界：** /my-enterprise 必须经过既有 enterprise RoleGuard；个人、政府、管理员没有企业入口，直接访问也不能渲染企业信息。
- **视觉决定：** 企业信息采用现有页面系统的无嵌套卡片信息网格，桌面双列、小屏单列；不新增公共导航、不改变政策/问答/咨询 API。
- **验收：** 个人/企业渲染合同分别确认四项/五项导航，企业信息字段来自 identity.organization，非企业角色拒绝；前端全量测试全部通过，生产构建通过（94 modules），OpenSpec strict 通过。浏览器访问 `/my-enterprise` 在未登录状态只显示“需要登录”，不渲染企业信息；移动端单列网格与横向导航断点由现有响应式样式及 render contract 覆盖。未使用真实账号或修改浏览器会话。

### B18-004 | 政策中心与历史问答查询性能定位

- **用户期望：** 点击“政策中心”或“历史问答”后，列表内容应在约 1–2 秒内可见；冷启动或数据库连接恢复不应出现数秒级白屏。
- **当前链路：** 登录身份已由 AuthSessionCoordinator 先调用 `/me` 获取；页面挂载后分别调用 `GET /api/v1/policies?page=1&page_size=10` 或 `GET /api/v1/qa?page=1&page_size=10`。后端每次请求复用一个 request-scoped SQLAlchemy session，先执行身份/组织/角色查询，再执行带 `count(*) over()` 的列表查询；列表只返回 10 条摘要，不读取全文字段。
- **测量口径：** 2026-08-23 在当前配置的 Supabase 数据库上做只读复测，使用已配置演示身份的 subject 注入测试 principal，仅绕过 JWT 验签，不绕过真实身份表和业务列表查询；未输出账号、令牌、连接信息或政策/问答文本，也未写入数据库。
- **实测结果：** 端到端 API 六次采样中，政策冷请求约 `6.0s`，热请求 `1.33–1.80s`（中位约 `1.46s`）；历史问答冷请求约 `1.81s`，强制释放连接池后一次冷请求约 `2.93s`，热请求 `1.41–1.88s`（中位约 `1.42s`）。每次均返回 10 条、总数 20。浏览器本地路由 HTML 返回约 `3–5ms`，无登录 API 约 `9ms`，因此前端静态壳不是主要瓶颈。
- **根因定位：** 强制冷连接追踪显示，政策请求新数据库连接建立约 `4.53s`，随后身份 SQL 约 `0.53s`、政策列表 SQL 约 `0.27s`；历史问答新连接约 `1.70s`，身份 SQL 约 `0.58s`、列表 SQL 约 `0.27s`。主要成本是 Supabase pooler 的连接建立/检活与网络往返，其次是每个请求都要进行身份查询；当前 20 条数据的文本读取和分页 SQL 不是主因。开发环境 `StrictMode` 还会让挂载型 `useEffect` 在开发模式重复发起请求，存在额外查询压力，需在后续优化中单独确认。
- **性能判断：** 热请求大体接近 1–2 秒目标，政策中心相对合理但已接近上限，历史问答处于可用但偏慢区间；冷启动政策请求约 6 秒明显不合理，是本项 P1 优先优化对象。
- **实现结果：** FastAPI lifespan 在启动阶段使用与请求复用的 SQLAlchemy engine 执行一次只读 `SELECT 1`，连接随后回到连接池；未配置数据库时跳过，预热失败只记录安全状态并继续启动。生命周期日志仅记录 `status` 和 `duration_ms`，不输出连接信息。
- **预热复测：** 启动预热耗时约 `4.99s`，该时间发生在服务启动阶段而非用户点击。预热后政策首次 API 请求约 `1.41s`，六次请求热中位约 `1.47s`（`1.37–2.11s`）；历史问答首次约 `1.54s`，热中位约 `1.54s`（`1.47–1.60s`）。两类请求均返回 10 条、总数 20，未写入数据库。
- **边界与遗留：** 本项只解决进程启动时的冷连接；Supabase 在长时间空闲后主动回收连接时，仍可能再次发生连接恢复延迟。后续如实测仍超出目标，再单独处理连接池生命周期、API/数据库部署区域和开发环境重复请求，不在本项引入缓存或数据库迁移。

### B18-005 | 主动退出返回公开首页

- **实际表现：** 用户在政策、问答、互动或角色工作区点击“退出登录”后，认证状态被清除，但当前路由不变，因此原页面就地显示“需要登录”和登录按钮。
- **期望行为：** 主动退出应清除本地会话并直接回到公开三入口首页 `/`；退出动作使用历史替换，浏览器后退不应恢复退出前的受保护地址。
- **状态边界：** 仅主动点击退出强制返回 `/`。会话自然过期或未登录用户直接访问受保护地址时，仍保留原有 RouteGuard 的明确登录提示。远端退出失败时，既有协调器仍先清除本地会话，公开页不得泄露私有内容或错误细节。
- **实现决定：** 顶部退出按钮调用既有 `signOut` 后立即以 `replace` 导航到 `/`；登录角色不匹配弹窗中的“切换账号”继续停留 `/login` 并保留入口意图，不复用本次全局退出跳转。

### B18-006 | 分离公开首页与登录后首页

- **实际表现：** 个人和企业从对应入口登录后分别进入 `/personal`、`/enterprise`，但这两个角色工作区已从精简导航删除；导航栏“首页”则指向 `/`，使同一地址在未登录时显示三入口、登录后显示问答首页，URL 语义不清。
- **路由决定：** `/` 固定作为未登录公开首页；新增 `/homepage` 作为登录后的统一首页。已登录身份访问 `/` 时以历史替换跳转 `/homepage`；未登录身份访问 `/homepage` 时以历史替换返回 `/`。
- **登录决定：** 个人或企业账号从匹配入口登录成功后统一进入 `/homepage`；从不匹配弹窗选择进入实际个人/企业服务时也进入 `/homepage`；直接访问登录页成功后默认进入 `/homepage`。政府入口匹配时仍进入 `/government`，政府和管理员受保护工作区及授权不变。
- **导航决定：** 登录后的“首页”和品牌标识均指向 `/homepage`。个人/企业继续使用已确认的精简导航；政府/管理员保留既有业务导航与角色入口。
- **兼容边界：** `/personal`、`/enterprise`、`/government` 路由暂不删除，原有书签和显式角色访问仍由 RoleGuard 与后端授权保护；管理员 `/admin` 前端路由在后续 B18-010 实施时删除，本项只改变默认登录落点和首页语义。

### B18-007 | 三类账号注册与管理员审批

- **确认决定：** 项目当前以 standalone PostgreSQL 作为唯一认证和业务数据底座，不再以 Supabase Auth 作为注册实现依赖。个人服务支持自助注册；企业服务和政府服务均提交注册申请，审批通过后才创建或激活正式账号与角色。
- **个人注册：** 通过 `/register?role=individual` 提交账号、密码、确认密码和显示名称。后端事务内创建 `app.users`、深圳 profile 和 `individual` 角色，注册成功后跳转登录页，不自动授予其他角色。
- **企业申请：** 通过 `/register?role=enterprise` 填写企业主体信息、使用人信息（使用人姓名、职务、联系方式）和登录信息。申请进入 `pending`，管理员审批通过后事务性创建企业组织、账号、profile 和 `enterprise` 角色；拒绝必须记录原因。
- **政府申请：** 通过 `/register?role=government` 先从现有深圳政府部门目录选择部门；一个部门最多只能有一个待审或已启用账号。选定部门后填写使用人信息和登录信息，管理员审批通过后事务性创建政府账号、组织绑定、`government` 角色和部门关系。沿用现有“一部门一个政府账号”的绑定模型，不在本项改造成多账号队列。
- **管理员页面边界：** 注册页面和管理员审批页面独立设计、独立路由、独立验收，但作为同一 B18-007 联合开发。管理员页面具体范围见 [`PRD-V1-B1-08-ADMIN-APPROVAL`](./PRD-V1-B1-08-ADMIN-APPROVAL.md)。
- **方案文档：** 注册与申请流程见 [`PRD-V1-B1-08-REGISTRATION`](./PRD-V1-B1-08-REGISTRATION.md)；管理员审批页面、接口、幂等和权限见 [`PRD-V1-B1-08-ADMIN-APPROVAL`](./PRD-V1-B1-08-ADMIN-APPROVAL.md)。实现前需据此补充 TECH/OpenSpec 和数据库迁移设计。

### B18-008 | 注册页面与管理员入口体验

- **问题：** 三类注册页面沿用登录页布局残留，表单卡片相对视口偏左；个人注册成功后表单仍保留，只在内部显示成功文字；公开首页缺少管理员登录入口。
- **实现：** 注册页面改为单列定宽容器，标题和 620px 表单共用水平中心线；移动端使用视口减 36px 宽度。个人注册成功后卸载完整表单，展示独立成功提示卡、立即登录按钮和 3 秒倒计时自动跳转。公开首页三服务卡片下增加低对比灰色“管理员登录”，进入 `?role=admin` 的管理员登录态。
- **视觉验收：** 无头 Chrome 实测个人、企业、政府注册卡片在 `1440x900` 下 `left=410/right=410/width=620/delta=0`；在 `390x844` 下 `left=18/right=18/width=354/delta=0`，六种组合横向溢出均为 0。截图人工核验标题、卡片、表单控件及页脚未重叠。
- **交互验收：** 真实创建一次个人测试账号后，成功瞬间 `.registration-panel` 数量为 0、`.registration-success-card` 为 1；立即跳转按钮指向 `/login?role=individual`，3 秒后 URL 自动切换到相同登录地址。管理员入口在桌面和移动端均可见，颜色 `rgb(146, 153, 168)`，链接为 `/login?role=admin`。

### B18-009 | 管理员政策录入与批量 Markdown 发布

- **确认决定：** 管理员政策中心同时支持手工表单和 Markdown 批量导入。每批最多 20 个 `.md` 文件，单文件最大 2 MB，不设置整批总大小上限；解析、校验、编辑和预览完成后才允许保存草稿或发布。
- **实现：** standalone PostgreSQL `0007_admin_policy_publishing` 增加政策来源/发布状态/管理员字段和审计事件；既有 20 条政策保持原始 ID/正文哈希不变并标记为 `published/external_url`。管理员新增政策使用 `manual` 或 `markdown` 来源，普通政策 API 只读取 `published`。
- **Markdown 合同：** UTF-8 flat YAML front matter 解析固定字段，提供 `/api/v1/admin/policies/markdown-example` 下载示例；批量接口逐文件返回 `ready/warning/failed`，失败项不阻断其他文件。
- **页面：** 当前实现的 `/admin/policies` 与 `/admin/policies/new` 将在 B18-010 实施时迁移为 `/policy-management` 与 `/policy-management/new`；政策管理继续只通过管理员首页特殊入口进入，不进入一级导航，非管理员 API 和页面均拒绝。
- **验收证据：** 管理员真实创建并发布 1 条 Markdown 政策、创建并发布后撤回 1 条手工草稿；混合批次 1 条成功/1 条失败隔离；示例解析、重复发布拒绝、普通用户 published-only、撤回后详情 404、非管理员 403、审计事件和桌面/移动无溢出均通过。

### B18-010/B18-011 | 管理员首页精炼与账号管理

- **确认调整：** 按用户反馈，管理员不再使用独立 `/admin` 页面，也不保留“平台管理”模块名称。管理员工作台直接由 `/homepage` 根据 `admin` 身份渲染；全局导航只保留首页、政策中心、历史问答。

- **账号管理：** 新增账号列表、详情、新增、编辑、停用/恢复能力，支持个人、企业、政府和管理员账号；物理删除不纳入，统一使用停用并保留历史和审计。
- **方案文档：** 详细产品、路由、字段、权限、API、停用策略和审计设计见 [`PRD-V1-B1-08-ADMIN-HOMEPAGE-AND-ACCOUNTS`](./PRD-V1-B1-08-ADMIN-HOMEPAGE-AND-ACCOUNTS.md)。
